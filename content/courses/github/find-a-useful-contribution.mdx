## Start with a project you understand as a user

Choose an open source tool you use or are willing to learn. Check its license, recent activity and contribution guidelines. Look for how maintainers handle questions and proposals. A beginner label can help you navigate issues, but it does not guarantee that a task is available or suitable.

Find a small problem you can reproduce: unclear setup, a missing example, an incorrect error message or a bug. Search existing issues and pull requests before proposing work. Follow the project's process; ask a focused question when expectations or ownership are unclear.

You can contribute documentation, tests, a reproduction or a review observation as well as code. Match the contribution to an actual need. Mass-produced changes and unnecessary rewrites create review work for maintainers without necessarily helping users.

## A worked example

Maya follows a library's quickstart and finds that one example uses an outdated argument. She checks the installed version, searches existing discussions and confirms the issue is not already covered. The guidelines ask for an issue before a change, so she opens one with the command, observed output and expected behavior.

A maintainer may propose a different fix or decline the change. The exercise still teaches her how to gather context and communicate a reproducible problem.

## Your turn · 45 minutes

1. Select one tool and read its contribution instructions.
2. Reproduce a small issue or identify a useful documentation gap.
3. Search for existing discussion and check whether the task is already claimed.
4. Draft the smallest proposal the project would need to evaluate it.

**Leave with:** a contribution plan containing context, scope and validation. You decide whether to submit it yourself. There is no requirement to contribute to a famous repository, and no promise that the change will be accepted. Respect the community's process and your own available time.
