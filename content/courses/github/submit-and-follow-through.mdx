## Make review easier for someone else

Work on a separate branch, keep the change focused and run the project's required checks. Read the diff before submitting. Remove unrelated formatting or generated files unless the project's process requires them. Explain the problem, the change and how you checked the result.

A useful pull request description lets a reviewer reproduce the issue and understand why the solution is appropriate. Link the related issue when there is one. For a bug fix, describe behavior before and after. For documentation, test the instructions or example you changed.

Respond to review with curiosity. Clarify the concern and update the work when appropriate. If you disagree, explain the evidence and tradeoff respectfully. If you cannot continue, tell the maintainer rather than leaving them to guess. Never imply that an unmerged proposal has already shipped.

## A worked example

Maya submits a quickstart correction. Her description includes the library version, the failing command and the corrected output. A maintainer asks her to update a second example. She makes that related change and reruns both examples.

Her portfolio note reads “Proposed a quickstart correction; awaiting review” until the status changes. If accepted, she can link the merged change and explain what she learned without claiming ownership of the library.

## Your turn · time depends on the change

1. Implement the smallest agreed change and inspect your diff.
2. Run required checks and record what remains untested.
3. Draft a description with problem, solution and validation.
4. Follow the project's submission process if you choose to contribute. Track the actual review status.

**Leave with:** a reviewable change or a complete practice draft. Write a short reflection on what was harder than expected. The value lies in learning collaboration and improving something useful, not in accumulating pull requests or badges.
